Each has a recommendation. Pick on the page and press Queue, or answer the input card the orchestrator sends.

D1. Where the map reads from.
The lane template's units.tsv gains three optional columns (milestone, after, since) and a fixed state vocabulary. The job-tracker lane still writes the old five-column log, which the approved phase 2 restructure converts. Until then its lane shows a one-line "legacy layout" notice.
D2. Where PR state comes from.

D3. How dependencies are drawn.
Standing order 37 ended stacked PRs, so most units have zero or one dependency. The mockup nests a unit under the one it waits for and writes the rest as text. A drawn graph would mostly be loose nodes, and on the phone it would still have to become this list.
D4. When to build it.
Your 14:01 rule starts nothing new before the Thu 15 Oct reset. The build is one dotfiles unit: a /map route, a parser with a fixture test per failure case, and a phone screenshot on the tailnet. About the size of the board itself.

What it answers

The board today lists threads. It cannot say what those threads are for, what is done, or what is parked on you. The map is a second page on the same server, /map, read from the lane files the coordinators already keep. It answers four questions per lane: which milestone is how far along, which unit waits on which, who holds each unit and whether that thread is alive, and what is on you right now.

What agenttrail read from a PLAN.md we already hold in ~/orchestrator/lanes/<lane>/. So no hooks, no second process, no file any repo has to carry, and no writes. The board keeps rendering on request.

Column rules

  • unit: [a-z0-9][a-z0-9-]*, unique in the file. Today's leading # is accepted and dropped.
  • state: exactly one of queued, in-flight, review, needs-myuser, blocked, paused, done. Anything else skips the row and is counted in the footer.
  • owner: a T3 thread id, or empty for unassigned. Prose like "worker (opus high)" shows as that text with no live state.
  • pr: a number, or a short word for things that are not PRs ("rebuild", "docs"). Numbers get the ledger chip and the GitHub link.
  • after: comma-separated unit ids, lane/unit for another lane. An id that matches nothing is drawn as after ? name and counted.
  • since: HH:MM today, or an ISO timestamp.
  • Columns are matched by header name, so order and extra columns do not matter. A file without a unit or state header is rejected whole.

What stays with people

  • The coordinator writes after, milestone and needs-myuser. The map shows exactly what was written. Nothing is inferred from prose, review notes or GitHub.
  • owners.md stays the human address book and is not parsed. The owner column carries the id.
  • Needs you on both pages = pending T3 input cards and approvals, plus every needs-myuser unit whose after units are all done.
  • One standing-order line per lane: "a unit's row carries its milestone, its dependencies and whether it waits on the owner". A brief lint can check it later; the map does not.

Fresh, missing, malformed

The map renders on request like the thread page: it reads the lane files and the T3 database each time, about six files under 100 KB, in a few milliseconds. No watcher and no background work. The one cache, added 16 Oct, holds local git answers for the looks-stale check, keyed by commit, so a refresh adds one git for-each-ref per repo. The page refreshes itself every 15 seconds. Each lane header shows "updated N ago" from the newest file's modification time. It turns to no update for 3 h when its coordinator thread is running but no lane file has changed for two hours, and to no update since 21 Oct 16:31 after a day with no change, whoever runs the lane.

How it flows

What it is not

  • Not a graph canvas. agenttrail's Map drew a repo's PLAN.md in WebGL and needed a daemon per repo. This is a list with nesting, on the server we already run.
  • Not a second writer. The coordinator's units file is the source; the map never edits it. Its one inference, added 16 Oct, is the looks-stale line on a needs-myuser row whose branch already landed.
  • Not a GitHub client. PR state is the ledger's last verdict; the chip links out for the live view (D2).
  • Not on the product repos. No PLAN.md, no hooks, no settings, no CLAUDE.md edits anywhere.

Risks

  • The map is only as honest as the coordinator's rows. A unit nobody marks needs-myuser never reaches Needs you. The thread page's input cards still catch the T3 side. The one-line standing order and, later, a brief lint carry the rest.
  • The job-tracker lane shows nothing useful until phase 2 converts its log. Phase 2 was approved on 10 Oct and waits for a quiet merge queue, which the 14:01 rule makes likely this week.
  • Cross-lane dependencies (the CI PR on your rebuild) need the lane/unit form. The map resolves it or shows "after ? name"; it never silently drops the edge.
  • Thread titles and unit ids are readable by every device on the tailnet, as the thread page already is.
