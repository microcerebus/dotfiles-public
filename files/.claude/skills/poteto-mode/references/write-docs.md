# Write docs

You own the reader's path through the doc.

1. Read `technical-writing/SKILL.md` and follow it.
   Each doc takes one Diátaxis mode: tutorial, how-to, reference or explanation.
   Split a doc that mixes them.
2. For shared code others will use (a package, a CLI, a skill, a service API), write the tutorial first, before the code.
   Design back from the calls the tutorial shows; the tutorial is then the target the build checks itself against.
3. For a high-stakes doc (an RFC, a design others will build on), draft it through `arena/SKILL.md` and keep the strongest draft.
4. Run every command and code sample in the doc exactly as written.
5. Apply unslop, put each sentence of long Markdown on its own line, and never use the em dash.
6. A plan doc is a how-to, and it follows `references/plan.md`.

**Reply.**
The doc's path, its mode, and what you ran to check it.
